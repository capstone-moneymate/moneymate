# 머니메이트 개발 분담표 (A·B·C 조정안)

2026-10-09 · 12/4 마감 · 팀원 3명 · 모두 금융 데이터 트랙 + 서버·화면을 하나씩 · @서현민

## 1. 분담 원칙과 변경 요지

- 이전 안(A 데이터 / B LLM·검증 / C 웹)에서 모두 A를 원했고 B가 너무 어려웠다. 그래서 세 명이 금융 데이터 트랙을 하나씩, 서버·화면을 한 탭씩, LLM 계열 일을 하나씩 나눠 갖도록 다시 짰다.

- 이 문서의 A·B·C는 이전 문서의 A·B·C와 뜻이 다르다. 이 문서가 최신이다.

- 모듈마다 담당자 1명이 끝까지 설명할 수 있어야 한다. 직접 실행해 결과를 확인하고, 겹침 계산과 검증기는 pytest로 테스트하며, 기능마다 커밋한다.

- 공통 파일(스키마, CLAUDE.md, config, db 연결)은 A만 수정한다. 나머지는 A에게 요청하거나 PR로 올린다. 각자 브랜치(또는 git worktree)에서 작업한다.

- **짝 리뷰: 막히면 크게 흔들리는 모듈은 짝이 PR을 같이 본다. C의 출제 파이프라인(classify·compose·reasons)은 B가, 탭1 화면·API(news.ts·answers.ts)는 A가 리뷰한다. B가 검증기를, A가 채점을 만들기 때문에 서로 연결되는 부분을 가장 잘 알기 때문이다.**

|------|------------------------------------------------------|---------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------|

## 2. 업무량과 난이도 균형

업무량 점수는 모듈별 작업량을 1~5로 추정해 더한 값이다. 난이도 종류는 서로 달라서, 각자 가장 위험한 한 곳에는 미리 안전장치를 둔다.

| 담당 | 업무량(추정) | 난이도   | 가장 위험한 곳                                                                               | 막혔을 때 안전장치                                                                                                                                                                         |
|------|--------------|----------|----------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| A    | 약 24        | 중상 (4) | 겹침 계산이 틀리기 쉽음. 1주차 인프라와 5~6주차 탭2가 바쁨. TradingAgents 시험 결과가 불확실 | 손계산 예시를 정답으로 둔 pytest. 채점은 키워드 규칙을 먼저 만들고 Claude 채점을 위에 얹음. TradingAgents는 확정안대로 1주 시험 후 안 되면 빼고 진행                                       |
| B    | 약 22.5      | 중상 (4) | ETF 보유 내역을 못 구할 수 있음(9/30 포함). 외부 데이터 의존                                 | 수집 폴백 순서: pykrx → 운용사 파일 → 팀원이 매일 받는 반자동. 9/30을 못 구하면 추세 기준일을 수집 시작일로                                                                                |
| C    | 약 24        | 중상 (4) | 출제 프롬프트 품질이 불확실. 3주차가 가장 빡빡                                               | 문제 1개당 비용이 높으면 Haiku 비중을 늘리고 Batch API(50%) 전환을 검토. 안 풀리면 사람이 만든 문제 템플릿으로 대체. 검증기(B)가 2주차에 먼저 끝나야 함. **출제는 B가, 탭1은 A가 짝 리뷰** |

LLM을 쓰는 부분은 A의 판단 채점·주관식 피드백과 C의 출제·이유 생성이고, B는 데이터·코드·검증 중심이며 LLM은 proposals.py의 2회 추출 정도다. 이유 생성(reasons.py)은 출제와 같은 패턴을 재사용하므로 C가 이어서 맡는다.

## 4. 팀원별 큼직한 할 일

### A — 13F·겹침·탭2·채점

1.  **기반 (1주차, 금요일 마감).** 레포, Docker Compose PostgreSQL, 스키마 13개 테이블, CLAUDE.md, docs/. B·C가 이걸 기다린다. 13F 4명 법인도 확인한다. 공통 저장 규칙(7장) 초안을 conventions.md에 올린다.

2.  **13F 수집과 큰손 변화 (2주차).** edgartools + OpenFIGI로 13F를 받고, 수량 기준 변화와 "늘림" 기준(+N%)을 계산한다. 개발은 2분기(6/30) 데이터로 한다.

3.  **겹침 판정 (2~3주차).** overlap.py로 큰손과 ETF의 방향(같은 방향/방향 다름)을 같은 시점 기준으로 비교한다. B의 etf_trend 결과를 받아 쓴다. 손계산 예시로 pytest를 완성한다.

4.  **판단 채점과 주관식 피드백 (3~4주차).** 키워드 규칙 채점(rule_judge.py)을 먼저 만들고, Claude 루브릭(증거 2·추론 3·반박 2)을 얹는다. 금지 표현이 나오면 고정 문구로 대체한다. 유형 3 주관식 피드백(잘한 점, 더 생각할 점, 인과 뼈대)도 같은 루브릭으로 만든다. judgement.ts에 일일 호출 제한과 해시 재사용.

5.  **탭2 API와 화면 (5~6주차).** overlap.ts, 겹침 메인(상단 겹침·하단 분석), 종목 상세 카드 ①②③, 안내 문구. 11/14 공시 후 3분기 13F로 갱신한다. 카드 ②의 이유는 C의 reasons.py, "내 지도에 있어요"는 B의 개념 사전과 연결한다.

6.  **개념↔티커 매핑과 TradingAgents 시험 (6주차).** B의 개념 사전을 기준으로 개념↔티커 매핑 테이블을 만들어 탭2의 "내 지도에 있어요"와 연결한다. TradingAgents는 탭1 해설 재료로 1주 시험한다(Claude 연결, 비용·시간, 한국어 품질, 분석 리포트와 낙관·비관 토론만 저장하고 매매 결론은 버림). 안 되면 빼고 진행한다.

7.  **채점 결과 제공 (7주차).** C가 κ를 계산할 수 있게 답안 40개를 judge.py로 채점해 점수를 넘긴다.

8.  **짝 리뷰.** C의 탭1 화면·API(news.ts·answers.ts) PR을 리뷰한다.

### B — ETF·사전·검증·탭3

1.  **ETF 확인과 수집 (1~2주차).** pykrx로 TIME 미국나스닥100액티브(426030)·KoAct 구성종목과 보유 수량을 확인하고 일일 스냅샷 수집을 오늘부터 시작한다. 안 되면 운용사 파일 → 반자동으로 내려간다.

2.  **개념 사전과 경로 탐색 (1~4주차).** 개념 17개 초안은 3명이 같이 쓰고 B가 정리해 DB에 넣는다. graph.py(경로 탐색·순환 검사)와 pytest를 만들고, 4주차에 proposals.py(사전에 없는 개념을 LLM이 제안 → 2회 독립 추출이 같고 순환이 없으면 후보 → 팀 승인 후 추가)를 만든다.

3.  **검증기 (2주차).** schemas.py와 validators.py(형식·정답 재계산·금지 표현·중복·근거 날짜). C의 출제가 쓰므로 2주차에 먼저 끝낸다.

4.  **ETF 추세와 보정 (2~3주차).** etf_trend.py로 분기 말 대비 추세와 전 거래일 대비 변화를 따로 계산하고, 자금 유입 보정(종목별 변화율에서 ETF 전체 변화율 중앙값 빼기)을 넣는다.

5.  **지표와 차트 읽기 화면 (3~4주차).** indicators.py(RSI·거래량 상위일·수익률)와 탭1의 차트 읽기 단계 화면(lightweight-charts).

6.  **탭3 (5~6주차).** React Flow 시험(개념 30~50개에서 확대·이동·접기), user_concepts 기록, mypage.ts, 인과 지도, 다시 보는 개념(정답률 낮은 순).

7.  **짝 리뷰.** C의 출제 파이프라인(classify·compose·reasons) PR을 리뷰한다.

### C — 뉴스·출제·탭1

1.  **시작 (1주차).** web 초기화(390×844), 탭 3개 라우팅, 탭1 뉴스 홈을 목 데이터로. 네이버 뉴스 API 샘플 20건 확인, Anthropic 월 한도 설정, Claude 호출 1회와 llm_cost_log.

3.  **출제 파이프라인 (3주차).** llm_client.py(월 한도·비용 로그), classify.py(유형 분류·개념 매칭, Haiku), compose.py(출제, Sonnet), 재생성 루프(최대 3회), pending 저장. 문제 1개당 비용을 측정한다(3~5주차). B가 짝 리뷰한다.
