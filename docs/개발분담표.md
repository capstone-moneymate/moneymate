# 머니메이트 개발 분담표 (A·B·C 조정안)

2026-10-09 · 11/20 기능 동결 · 12/4 마감 · 팀원 3명 · 모두 금융 데이터 트랙 + 서버·화면을 하나씩 · @서현민

## 1. 분담 원칙과 변경 요지

- 이전 안(A 데이터 / B LLM·검증 / C 웹)에서 모두 A를 원했고 B가 너무 어려웠다. 그래서 세 명이 금융 데이터 트랙을 하나씩, 서버·화면을 한 탭씩, LLM 계열 일을 하나씩 나눠 갖도록 다시 짰다.
- 이 문서의 A·B·C는 이전 문서의 A·B·C와 뜻이 다르다. 이 문서가 최신이다.
- 모듈마다 담당자 1명이 끝까지 설명할 수 있어야 한다. 직접 실행해 결과를 확인하고, 겹침 계산과 검증기는 pytest로 테스트하며, 기능마다 커밋한다.
- 공통 파일(스키마, CLAUDE.md, config, db 연결)은 A만 수정한다. 나머지는 A에게 요청하거나 PR로 올린다. 각자 브랜치(또는 git worktree)에서 작업한다.
- 기술확정안 v3(에이전트 반영)에 맞춰 서버(Spring Boot), 1차 자료 수집, 출제·검토 에이전트, 판단 채점 구조(FastAPI 채점 서버), 배포를 고쳤다. v3가 최종 확정되면 다시 맞춘다.
- **짝 리뷰: 막히면 크게 흔들리는 모듈은 짝이 PR을 같이 본다. C의 출제 파이프라인(classify·출제 에이전트·reasons)은 B가, 탭 1 화면·API(뉴스·답안 API)는 A가 리뷰한다. B가 검증기를, A가 채점을 만들기 때문에 서로 연결되는 부분을 가장 잘 알기 때문이다.**

| 담당 | 금융 데이터 트랙 | 서버 + 화면 | 그 외 |
| :--- | :--- | :--- | :--- |
| A | 13F 수집(CUSIP→티커), 큰손 변화 계산, 겹침 방향 판정 | 탭 2 (겹침 API, 겹침 메인, 종목 상세) | 레포·Docker·스키마·CLAUDE.md, 판단 채점(FastAPI 채점 서버, 규칙→Claude 루브릭)과 판단해보기 AI 분석 피드백, 개념↔티커 매핑, TradingAgents 시험 |
| B | ETF 수집, 추세·어제 변화, 지표 계산 | 탭 3 (마이페이지 API, 인과 지도) + 탭 1의 차트 읽기 화면 | 개념 사전·경로 탐색·사전에 없는 개념 제안(proposals.py), 검증기 |
| C | 가격·1차 자료 수집, 1차 자료 선별, 이벤트 날짜표 | 탭 1 (뉴스·답안 API, 화면 전체) | 출제 파이프라인(Haiku 분류·Sonnet 출제 에이전트), llm_client.py, 탭 2 이유 생성, 유형 3 학습 화면, 채점 신뢰도(κ), run_daily.py, 배포 |

v3에 새로 생긴 검토 에이전트(독립 풀이·모호함 판정)는 담당 미정이다. 팀이 정한 뒤 이 표에 넣는다.

## 2. 업무량과 난이도 균형

업무량 점수는 모듈별 작업량을 1~5로 추정해 더한 값이다. 난이도 종류는 서로 달라서, 각자 가장 위험한 한 곳에는 미리 안전장치를 둔다.

| 담당 | 업무량(추정) | 난이도 | 가장 위험한 곳 | 막혔을 때 안전장치 |
| :--- | :--- | :--- | :--- | :--- |
| A | 약 24 | 중상 (4) | 겹침 계산이 틀리기 쉬움. 1주차 인프라와 5~6주차 탭 2가 바쁨. TradingAgents 시험 결과가 불확실 | 손계산 예시를 정답으로 둔 pytest. 채점은 키워드 규칙을 먼저 만들고 Claude 채점을 위에 얹음. TradingAgents는 확정안대로 1주 시험 후 안 되면 빼고 진행 |
| B | 약 22.5 | 중상 (4) | ETF 보유 내역을 못 구할 수 있음(9/30 포함). 외부 데이터 의존 | 수집 폴백 순서: pykrx → 운용사 파일 → 팀원이 매일 받는 반자동. 9/30을 못 구하면 추세 기준일을 수집 시작일로 |
| C | 약 24 | 중상 (4) | 출제 프롬프트 품질이 불확실. 3주차가 가장 빡빡 | 문제 1개당 비용이 높으면 Haiku 비중을 늘리고 Batch API(50%) 전환을 검토(도구 루프에 쓸 수 있는지 확인 후). 안 풀리면 사람이 만든 문제 템플릿으로 대체. 검증기(B)가 2주차에 먼저 끝나야 함. **출제는 B가, 탭 1은 A가 짝 리뷰** |

LLM을 쓰는 부분은 A의 판단 채점·주관식 피드백과 C의 출제 에이전트·이유 생성, 그리고 담당 미정인 검토 에이전트이고, B는 데이터·코드·검증 중심이며 LLM은 proposals.py의 2회 추출 정도다. 이유 생성(reasons.py)은 출제와 같은 패턴을 재사용하므로 C가 이어서 맡는다.

## 4. 팀원별 큼직한 할 일

### A — 13F·겹침·탭 2·채점

1. **기반 (1주차, 금요일 마감).** 레포, Docker Compose PostgreSQL, 스키마 13개 테이블, CLAUDE.md, docs/. B·C가 이걸 기다린다. 13F 4명 법인도 확인한다. 공통 저장 규칙(6장) 초안을 conventions.md에 올린다.
2. **13F 수집과 큰손 변화 (2주차).** edgartools + OpenFIGI로 13F를 받고, 수량 기준 변화와 "늘림" 기준(+N%)을 계산한다. 개발은 2분기(6/30) 데이터로 한다.
3. **겹침 판정 (2~3주차).** overlap.py로 큰손과 ETF의 방향(같은 방향/방향 다름)을 같은 시점 기준으로 비교한다. B의 etf_trend 결과를 받아 쓴다. 손계산 예시로 pytest를 완성한다.
4. **판단 채점과 주관식 피드백 (3~4주차).** 키워드 규칙 채점(rule_judge.py)을 먼저 만들고, Claude 루브릭(증거 2·추론 4·반박 3)을 얹는다. 금지 표현이 나오면 고정 문구로 대체한다. 판단해보기 주관식 근거에 대한 AI 분석 피드백(잘한 점, 더 생각할 점, 인과 뼈대)도 같은 루브릭으로 만든다 (모든 유형 공통). 규칙 채점과 Claude 채점을 하나의 Python 채점 함수로 묶어 FastAPI 채점 서버(judge_api.py)로 띄우고, Claude 호출이 실패하면 같은 함수 안에서 규칙 채점으로 넘어간다. Spring Boot의 판단 채점 API는 FastAPI를 HTTP로 호출하고, 일일 호출 제한·해시 재사용과 호출 실패 시 고정 문구를 맡는다.
5. **탭 2 API와 화면 (5~6주차).** 겹침 API, 겹침 메인(상단 겹침·하단 분석), 종목 상세 카드 ①②③, 안내 문구. 11/14 공시 후 3분기 13F로 갱신한다. 카드 ②의 이유는 C의 reasons.py, "내 지도에 있어요"는 B의 개념 사전과 연결한다.
6. **개념↔티커 매핑과 TradingAgents 시험 (6주차).** B의 개념 사전을 기준으로 개념↔티커 매핑 테이블을 만들어 탭 2의 "내 지도에 있어요"와 연결한다. TradingAgents는 탭 1 해설 재료로 1주 시험한다(Claude 연결, 비용·시간, 한국어 품질, 분석 리포트와 낙관·비관 토론만 저장하고 매매 결론은 버림). 안 되면 빼고 진행한다.
7. **채점 결과 제공 (8주차).** C가 κ를 계산할 수 있게 답안 40개를 judge.py로 채점해 점수를 넘긴다.
8. **짝 리뷰.** C의 탭 1 화면·API(뉴스·답안 API) PR을 리뷰한다.

### B — ETF·사전·검증·탭 3

1. **ETF 확인과 수집 (1~2주차).** pykrx로 TIME 미국나스닥100액티브(426030)·KoAct 구성종목과 보유 수량을 확인하고 일일 스냅샷 수집을 오늘부터 시작한다. 안 되면 운용사 파일 → 반자동으로 내려간다.

| 항목 | 규칙 | 예 |
| :--- | :--- | :--- |
