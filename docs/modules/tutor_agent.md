# worker/tutor/agent.py (+ mastery.py, demo.py)

- **한 줄 설명**: 퀴즈 앞 "개념" 단계를 사용자의 지식 상태에 맞춰 가르치는 튜터 에이전트 (계획 1-3, #201). 순서를 코드가 정하지 않고, 매번 도구 결과를 보고 모델이 다음 행동을 고른다.
- **입력**: `ConceptMap`(개념 이름·설명·선수 관계·헷갈리기 쉬운 이웃. 실제로는 `from_db`로 009·012 표에서 읽는다(`concepts.load_map`이 넣은 지도, 헷갈리는 이웃은 사람이 keep한 것만). `from_build`는 `concept_map.json`에서 만든다. 만들 때 #199 `break_cycles`로 순환을 끊는다), 목표 개념(`card_targets`: 카드 "개념" 단계 용어를 노드 이름·별칭과 `term_key`로 맞춘 것. `concept_node_cards`는 ②가 카드 글에서 찾은 용어까지 들어 있어 쓰지 않는다), 사용자 id, 지식 상태(`mastery`). 모델은 Opus 5.5, effort low (`llm_client.create`, module=`tutor`).
- **하는 일**: 도구 4개. `ready_concepts`는 목표 개념 전부의 상태(앎 / 준비됨 / 선수 개념 먼저 + 모르는 선수 개념)와 준비된 개념(알 확률, 헷갈리기 쉬운 이웃)을 코드가 계산한다. `ask_quiz(concept, kind)`는 퀴즈를 만들고(`tutor/quiz.py`) 세션을 `waiting`으로 멈춘다. `answer()`로 답이 오면 채점 → 지식 상태 갱신 → 결과(정답, 확신, 찍어서 맞힐 확률, 지금 알 확률)를 넘기고 다시 돈다. `explain(concept, style, text)`은 에이전트가 쓴 설명을 화면 이벤트로 보낸다(금지 표현은 되돌린다). `go_main`은 끝낸다. 모든 도구에 `reason`을 먼저 쓰게 해서 `log`에 "무엇을 왜"가 남는다.
- **출력**: `Session`. `status`(running / waiting / done / error), `finished_by`(go_main / quiz_limit / call_limit / no_tool / stop:이유), `log`(단계마다 도구·입력·이유·채점 결과), `events`(화면용: quiz / graded / explain / done. 정답은 넣지 않는다), `messages`(대화 전체. 이어 가려면 그대로 다시 보낸다).
- **지식 상태 (#230)**: `mastery.py`의 `DbMastery(conn, card_id)`가 사람2의 BKT(`learner/state.py`)를 쓴다. `get_mastery`는 `state.get_mastery`(안 풀어 본 개념은 처음 값 0.25), 답이 오면 `state.update`(추측 확률 `guess_p`, 확신, 응답 시간, 답 변경, 퀴즈 종류)로 고치고 `concept_answers`에 `source='tutor'`, `card_id`, `attempt_no`, 퀴즈 종류·추측 확률·퀴즈(정답 없는 화면용)·답·정답 여부·확신(1/2)·응답 시간·답 변경을 남긴다. 사람2의 확신 점검과 고스트("개념 단계 N문제 필요")가 이 기록을 읽는다. 답 하나마다 갱신과 기록을 함께 커밋한다(`state.py`는 커밋하지 않고 부르는 쪽이 한다). 다음 모델 호출 전에 커밋해서 그 호출이 실패해도 답은 남는다. **시도 번호**: 개념 단계는 카드의 첫 답 단계보다 먼저 푼다. 다시 풀 때 그 시점의 `user_answers` 최대 번호는 아직 지난 시도라서, 개념 단계 답은 그 사용자·카드의 최대 번호 + 1(기록 없으면 1)을 쓴다(사람2와 맞춘 규칙, #216). 세션에서 처음 답할 때 한 번 정하고 그 세션의 답은 모두 같은 번호다. 카드 없이 부르면 `card_id`·`attempt_no`는 비운다. 확신 글자(확신해요 / 애매해요)는 사람2의 `normalize_confidence`가 2 / 1로 바꾼다. `FakeMastery`는 DB 없는 테스트용으로만 남겼다(숫자에 근거가 없어서 평가·발표에 쓰지 않는다).
- **평가용 고리 (#238)**: `Session.max_quizzes`(세션마다 퀴즈 상한, 기본 `MAX_QUIZZES` 6. 프롬프트는 `<lesson>`의 값을 쓴다)와 `Session.quiz_maker`(퀴즈를 만드는 함수. 비우면 `make_quiz`로 Haiku 출제, 1-5 평가는 미리 만든 퀴즈 은행)를 두었다.
- **API (#240)**: 앱에서는 `tutor/api.py`(채점 서버 `/tutor`)와 Spring `TutorController`로 쓴다(tutor_api.md). graded 이벤트에 정답(`key`)과 종류(`kind`)를 넣었다(답한 뒤라 화면이 맞는 보기를 표시). API 는 `ShortConnMastery`로 읽고 쓸 때만 DB 연결을 연다.
- **모델을 고른 근거**: 2026-11-23 `scripts/measure_tutor_latency.py`로 튜터 한 단계와 같은 요청을 비교했다 (상황 6개 × 4번). 규칙대로 고른 비율 Opus 5.5 low 20/24, Sonnet 5.5 low 15/24. 평균 2.8초 대 5.2초 (Sonnet 최대 32.7초). 1회 $0.009 대 $0.005.
- **비용 (프롬프트 캐싱)**: 튜터는 매번 대화 전체를 다시 보내서, 요청에 `cache_control`(자동 캐싱)을 켰다. 앞에서 보낸 부분은 입력 단가의 0.1배로 읽고, 모델이 받는 내용은 같다. 2026-11-23 시연(학습자 2명)에서 켜기 전에는 호출 19번 $0.31(1번 평균 $0.016), 켠 뒤에는 20번 $0.12(1번 평균 $0.0058)였다. 처음엔 $0.13으로 기록됐는데, `llm_client`가 Opus 캐시 읽기를 입력 단가의 0.1배로 계산해서였다. Opus 5.5 캐시 읽기는 0.05배($0.20/1M)라 `PRICES`에 모델별 `cache_read_mult`를 두고 다시 계산했다 (#204 리뷰). 입력 토큰의 89%(62,454 중 55,856)를 캐시에서 읽었다. 캐시가 깨지지 않게 `SYSTEM`과 `tools()`에는 시각 같은 바뀌는 값을 넣지 않는다.
- **주의할 점**: 한 번에 도구 하나만 부르게 했다(`disable_parallel_tool_use`). Opus 5.5는 도구 강제(`tool_choice` any/tool)가 안 돼서, 글만 쓰고 도구를 안 부르면 한 번만 다시 부탁하고 그래도 안 부르면 끝낸다. 상한은 퀴즈 6개, 모델 호출 16번이다. 거절(`refusal`)이 오면 `error`로 끝낸다. 예상 못 한 오류(API 오류, 월 한도 `BudgetExceeded` 등)도 `error`(`finished_by="stop:오류 이름"`)와 `done` 이벤트를 남기고 오류를 그대로 올린다. 이어서 다시 돌리지는 않는다: 퀴즈를 만들다 실패하면 대화가 답 없는 `tool_use`로 끝나서, 다시 돌리려면 그 `tool_use`에 먼저 답해야 한다. 서버 대체 모델(fallbacks)은 `llm_client.create`가 베타 API를 쓰지 않아서 아직 켜지 않았다. **퀴즈 상한과 BKT**: 진짜 BKT는 처음 값 0.25에서(#245 전에는 0.3, 횟수는 같다) 4지선다를 세 번 연달아 맞혀야 0.95(앎)를 넘는다. 상한이 퀴즈 6개라 한 세션에서 "앎"까지 올릴 수 있는 개념은 2개쯤이다. 선수 개념이 긴 카드(자사주 소각: 선수 포함 6개)는 한 번에 목표까지 못 가고, 알 확률은 다음 카드·복습으로 이어진다(DB에 남으므로). 2026-11-24 상한은 6개로 유지하기로 했다(개념 단계는 본 문제 전 준비라 2~3분 안에, 못 올린 개념은 다음 카드·복습으로). 진짜 BKT에서 앎까지 연속 정답은 O/X 5번(#245 전 6번), 4지선다·짝 맞추기 3번, 칩 빈칸·사례 분류 2번이라, "거의 앎" 확인을 O/X 대신 칩 빈칸·사례 분류로 하도록 프롬프트를 바꿨다. 상한 6과 10 비교는 1-5 평가에 넣는다. 또 남은 퀴즈로 목표를 다 못 채울 때도 기준에 가까운 개념은 마저 올리고 끝내라고 한 줄 넣었다 (시연에서 0.94 두 개를 남기고 퀴즈 2개를 안 쓰고 끝냈다. 넣은 뒤에는 퀴즈 5개로 0.96·0.99). 같은 시연 두 번 모두 "자기주식 / 칩 빈칸" 출제가 모양 검사에서 실패해 튜터가 사례 분류로 바꿨다 (원인은 아직 안 봄). 세션은 아직 메모리에만 있다. 화면과 잇는 API(judge_api처럼 FastAPI)와 저장은 다음 단계다.
