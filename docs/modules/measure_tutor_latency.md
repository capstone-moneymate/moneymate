# worker/scripts/measure_tutor_latency.py

- **한 줄 설명**: 튜터 에이전트(#201) 모델을 고르려고, 튜터 한 단계와 같은 요청을 모델별로 보내 걸린 시간·고른 도구·비용을 잰 시험용 스크립트다. 실제 튜터 코드가 아니다.
- **입력**: 상황 6개(확신했는데 틀림, 처음 보는 개념, 헷갈리는 이웃, 거의 앎, 긴가민가, 목표 다 앎)와 상황마다 규칙상 맞다고 보는 선택. 조건은 Opus 5.5 low, Sonnet 5.5 low. 실행은 `cd worker && python -m scripts.measure_tutor_latency [반복 수]` (실제 API, 4번이면 약 $0.3).
- **하는 일**: 첫 연결 시간이 한 조건에만 섞이지 않게 한 번 먼저 부르고 버린다. 그다음 상황과 조건을 번갈아 부른다. 시간은 요청부터 응답까지 잰다. `llm_client.PRICES`에 Opus가 없던 때 만들어서 비용은 여기서 계산하고 `record`로 비용 기록에 남긴다.
- **출력**: 조건별 규칙대로 고른 수, 평균·90%·최대 시간, 1회 비용, 상황별 선택. `logs/tutor_latency.json`.
- **결과 (2026-11-23, 상황 6개 × 4번)**: Opus 5.5 low 20/24, 평균 2.8초, 90% 3.9초, 최대 5.9초, $0.009. Sonnet 5.5 low 15/24, 평균 5.2초, 90% 4.9초, 최대 32.7초, $0.005. 앞선 측정(상황 1개 × 5번)에서는 Opus가 평균 약 1초 느렸다. 속도 차이는 서버 상황에 따라 바뀌는 정도로 본다.
- **주의할 점**: 기준은 시스템 프롬프트에 쓴 규칙이라 "규칙을 얼마나 따르나"를 잰 것이지 교육적으로 맞는지를 잰 게 아니다. "거의 앎" 상황은 목표 개념 하나의 상태가 빠져 있어서 두 모델 모두 다시 확인하려 했다(설계 실수). 실제 튜터는 목표 개념 상태를 빠짐없이 준다.
- **테스트**: 실제 API를 불러야 해서 pytest에 넣지 않았다.
