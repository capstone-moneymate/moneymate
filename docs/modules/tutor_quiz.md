# worker/tutor/quiz.py

- **한 줄 설명**: 개념 단계 퀴즈 7종류를 만들고(Haiku), 모양을 검사하고, 채점하고, 찍어서 맞힐 확률을 코드로 계산한다 (#201).
- **입력**: 종류, 개념 이름, 개념 설명(desc, 정답의 근거), 헷갈리는 쌍이면 두 개념 이름, 짝 맞추기면 용어 3개. 호출은 `llm_client.create`(module=`tutor_quiz`), 종류마다 JSON 스키마를 쓴다.
- **하는 일**: 화면 A(보기 고르기)는 용어 뜻(3지선다), 헷갈리는 쌍(두 개념 이름), 틀린 설명(3개 중 틀린 것), O/X. 화면 B(칩을 칸에 넣기)는 칩 빈칸(칩 4개·빈칸 2개), 짝 맞추기(3쌍), 사례 분류(바구니 2개·사례 4개, 두 바구니 모두 사용). 코드 검사: 보기 수, 보기 중복, 정답 번호 범위, 헷갈리는 쌍 보기가 두 개념 이름 그대로인지, 빈칸과 정답 수, 금지 표현. 틀리면 한 번 더 만들고, 또 틀리면 `QuizError`.
- **출력**: `Quiz(kind, concept, content, key, explanation, guess_p)`. `content`는 화면용이라 정답이 없고, `key`는 서버만 본다. `grade(quiz, answer)`는 답이 `key`와 같은지 본다.
- **찍어서 맞힐 확률 (손계산)**: 용어 뜻·틀린 설명 1/보기 수(3지선다 33%), 헷갈리는 쌍·O/X 1/2, 칩 빈칸 1/(4×3) ≈ 8%, 짝 맞추기 1/3! ≈ 17%, 사례 분류 1/2⁴ ≈ 6%. 계획 1-3 표의 숫자와 같다. 튜터에게 넘기고, 나중에 BKT 추측 확률로 쓴다.
- **정답 위치 (#231)**: LLM 에게 칩 번호를 세게 하지 않는다. 2026-11-24 칩 빈칸 6번 중 5번 Haiku 가 칩 번호를 1부터 세서(코드는 0부터) 모양 검사는 통과하고 정답이 틀렸다(맞게 고른 학습자가 틀렸다고 나옴. 마지막 칩이면 4가 나와 출제 실패). 그래서 칩 빈칸 정답은 칩 글자 그대로 받고 (띄어쓰기는 무시) 코드가 번호로 바꾼다. 또 LLM 은 정답을 첫 보기에 두는 버릇이 있어서(용어 뜻·헷갈리는 쌍 4번 모두 0번) `generate`가 `shuffle`로 보기(용어 뜻·헷갈리는 쌍·틀린 설명)·칩·사례 순서를 섞고 정답 번호를 따라 옮긴다. 찍어서 맞힐 확률이 위 손계산대로 되려면 섞어야 한다. O/X는 늘 O, X. 짝 맞추기는 화면이 섞는다. 사람2의 `learner/review.py`도 보기를 섞는데, 한 번 더 섞여도 고르게 섞인 건 그대로라 괜찮다.
- **보기 칸 (#246)**: 용어 뜻·틀린 설명은 보기를 목록(`options`)이 아니라 칸 3개로 받는다 (용어 뜻 `correct`·`wrong_1`·`wrong_2`, 틀린 설명 `true_1`·`true_2`·`wrong`). 목록으로 받을 때 2026-11-25 '자사주 소각' 틀린 설명을 3번 연속 보기 4개로 내서 출제가 실패했고, 구조화 출력은 목록 길이 제약(minItems/maxItems)을 지원하지 않아 스키마로 막을 수 없었다. 칸 이름이 정답을 말해서 정답 번호(`answer_index`)도 LLM 이 세지 않는다(위 #231 과 같은 생각). `to_quiz`가 `options`(정답을 용어 뜻은 맨 앞, 틀린 설명은 맨 뒤)와 정답 번호를 만들고 `shuffle`이 섞어서, 화면·채점이 받는 모양은 그대로다. 헷갈리는 쌍은 보기가 두 개념 이름 그대로라 검사가 정확해서 목록 그대로 둔다. 같은 날 개념 10개 × 용어 뜻·틀린 설명 20번을 실제 모델로 출제해 19번 성공했고(모두 첫 시도, 보기 개수 실패 0), 실패 1번은 주당순이익(EPS) 틀린 설명이 3번 모두 "반드시 오른" 같은 주가 예측을 틀린 보기로 써서 금지 표현 검사에 걸린 것이었다. 틀린 보기라도 화면에 보이므로 검사는 그대로 두고, 안내(`HOW`)에 "틀린 설명에도 주가 예측은 쓰지 말고 뜻·계산을 잘못 아는 오개념을 쓴다"를 넣었다 (넣은 뒤 EPS 5번 포함 8번 모두 성공).
- **내용 검사 (#234)**: 정의를 묻는 문제는 코드가 맞는지 계산할 수 없어서, 칩 빈칸·용어 뜻·틀린 설명·사례 분류는 출제와 **따로 부르는** 검사(`check`, Haiku)를 거친다. 퀴즈를 "참이어야 하는 문장 / 거짓이어야 하는 문장"으로 펼치고(`claims`: 칩 빈칸은 칩 2개를 빈칸에 넣는 모든 경우 12가지로 정답 순서만 참이고 정답 두 칩을 바꿔 넣은 것도 거짓, 용어 뜻은 "개념의 뜻: 보기", 틀린 설명은 보기 그대로, 사례 분류는 사례마다 두 바구니 모두 "사례 → 바구니"로 고른 바구니만 참, 해설이 있으면 "해설: …"도 참이어야 함. 정답 말고 다른 답도 맞는 퀴즈와 해설이 틀린 퀴즈를 거른다, #237 리뷰), 어느 쪽이 정답인지는 숨기고 문장마다 참·거짓·애매를 묻는다(보여 주면 맞장구친다). 코드가 비교해서 참이어야 할 문장이 참이 아니거나, 거짓이어야 할 문장이 참이거나, 매수·매도 권유가 있으면 버리고 새로 낸다. 거짓이어야 할 문장이 애매(오답 칩을 넣어 말이 안 되는 문장)인 것은 학습자에게도 오답이라 통과시킨다 (애매까지 탈락시키면 칩 빈칸 5개 중 4번이 그 이유로만 다시 출제됐다). 그래서 다시 내는 횟수를 2 → 3으로 늘렸다. O/X·헷갈리는 쌍·짝 맞추기는 아직 검사하지 않는다. **칩 빈칸만 출제를 Sonnet으로** 한다(`GEN_MODEL`). 2026-11-24 측정(개념 5개 × 종류마다 2개, **Claude가 읽고 판정, 사람 검토 전**): 검사 전 칩 빈칸 3/10, 틀린 설명 3/9가 틀린 퀴즈(용어 뜻 0/9, 사례 분류 0/10). 검사 뒤 틀린 설명 0/9. 칩 빈칸은 Haiku로는 검사를 붙여도 10개 중 4개만 나오고 그중 2개가 틀려서("[영업이익]은 매출에서 [매출원가]를 뺀 값") Sonnet으로 바꾸니 10개 중 9개가 나오고 9개 모두 맞았다. 비용: 검사 한 번 약 $0.0003, Sonnet 칩 빈칸 한 개 약 $0.003. 퀴즈를 만드는 시간은 검사만큼 늘어난다.
- **주의할 점**: 정의를 묻는 문제는 정답이 맞는지 코드가 계산할 수 없다. 그래서 개념 지도 설명을 근거로 주고, 코드는 모양만 본다. 설명이 비어 있으면 LLM 지식에 기댄다. 짝 맞추기는 뜻을 용어와 같은 순서로 받고 화면이 섞는다. 답은 용어 순서대로 원래 뜻 번호다.
