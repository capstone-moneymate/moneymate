# worker/validate/validators.py

- **한 줄 설명**: LLM이 만든 인과 순서 문제를 개념 사전 계산 결과(`concepts/graph.py`)와 원문에 대조해, 통과 여부와 실패 이유를 돌려주는 검증기 최소 버전.
- **입력**: 퀴즈 dict(`start_concept`, `change`, `end_concept`, `answer_order`, `direction`, `evidence_quote`)와 원문 텍스트. 형식은 임시이고 C의 출제 결과 형식과 맞춘다. `g`를 주지 않으면 `db/seeds` 개념 사전을 쓴다. `regime`(그날 경기 국면, #174 regime.md)을 주면 경로·방향을 그 국면의 연결로 본다. 주지 않으면 평상시라 예전과 같다(예: 기준금리 인하 → 국채 금리 → 성장주는 평상시 ▲, 경기 침체 ▼).
- **하는 일**: ① 필드가 다 있고 `change`·`direction`이 up / down인지 ② 개념 id가 사전에 있는지 ③ 시작 → 결과 경로가 있는지 ④ 방향이 다른 경로가 함께 있으면 순서 문제로 부적합 ⑤ 정답 순서가 사전 경로 중 하나와 같은지 ⑥ 방향이 사전으로 계산한 방향과 같은지 ⑦ 인용한 근거가 원문에 그대로 있는지(띄어쓰기·줄바꿈 차이는 무시)를 검사한다.
- **출력**: `Report(errors, warnings)`. `errors`가 비어 있으면 `passed`. `errors`는 그대로 출제 단계에 돌려줘 다시 쓰게 하는 문장이다. `warnings`는 통과는 시키지만 사람이 확인할 것이다.
- **주의할 점**: 경로가 여러 개일 때는 그중 하나와 같으면 통과시키고 "원문 설명과 같은 경로인지 확인 필요" 경고를 붙인다(엄격하게 원문에 중간 개념이 나오는 경로만 통과시키면, 중간 과정을 적지 않는 공시가 많아 맞는 문제도 버릴 수 있어서). 같은 결론으로 가는 지름길 연결은 사전에서 빼서 경로를 줄인다(`rate_hike → growth_valuation` 직접 연결은 #66에서 지움). 근거 날짜(탭 2)는 아래 `check_evidence`(#121). 형식 검사는 C의 compose가 JSON 스키마로 하고(schemas.py는 만들지 않음, C와 합의), 숫자 재계산은 C의 tools.py가 한다.
- **테스트**: `cd worker && python -m pytest tests/test_validators.py -q` (손계산: 파월 예시는 인하 기대 down × (-1)×(-1)×(+1) = 하락 압력이 정답, 방향·순서·인용을 하나씩 틀린 불량 샘플, 모호한 쌍은 실패, 경로 2개는 통과 + 경고, 실제 사전의 인하 → 국채 금리 → 성장주).

## 중복 `find_duplicates(new_texts, past_texts, threshold=90) -> list[str]`
- **하는 일**: 새 문제 문장마다 예전 문제 중 가장 비슷한 것과 RapidFuzz `ratio`(문장 전체 글자 비교, 대소문자·문장부호 무시)로 비교해, 90점 이상이면 "다른 질문으로 바꿔 주세요" 오류 문장을 돌려준다. DB를 읽지 않는다. 예전 문제는 C가 `steps`에서 최근 N일치 quiz·chart 문제를 읽어 넘긴다. question만 넘기지 않고 question + 보기 문장을 이어서 넘기며, 새 문제도 같은 형식이어야 점수를 비교할 수 있다(#53 리뷰, C와 합의).
- **주의할 점**: 문장 비교만으로는 "말투만 바꾼 같은 질문"과 "같은 틀에 종목·사건만 바꾼 다른 질문"을 가를 수 없어서, **거의 같은 문장만** 잡기로 했다(B 결정). 2026-11-02 예시로 잰 점수(ratio / token_set_ratio): 완전히 같음 100/100, 같은 틀 다른 종목 86/93, 같은 틀 다른 사건 86/84(짧은 질문은 90을 넘을 수 있음: "금리 동결 이후 어느 쪽 흐름을 더 지켜볼까요?"와 "금리 인하 이후 …"는 ratio 92), 말투만 다른 같은 질문 75/77, 짧은 질문이 긴 질문에 포함 56/100, 전혀 다름 33/28. 기술확정안의 `token_set_ratio`는 포함 관계면 100이라 다른 문제를 잘못 거를 수 있어 쓰지 않았다. 판단해보기 질문은 틀이 비슷해 다른 사건도 걸리므로 C가 빼고 넘긴다. RapidFuzz는 `pyproject.toml`에 아직 없어 A에게 추가를 요청했다. 함수 안에서 불러오므로 설치 전에도 다른 검사는 쓸 수 있다.
- **테스트**: `python -m pytest tests/test_duplicates.py -q` (같은 문장·문장부호만 다름은 걸림, 같은 틀 다른 종목·사건, 포함 관계, 다른 질문은 통과, 기준값 조절, 빈 입력, 여러 개 보고).

## 근거 날짜 (탭 2) `check_evidence(chosen, available, base_date, where="") -> list[str]`
- **하는 일**: 탭 2 카드 ② 이유가 고른 근거 번호(`chosen`)를 입력으로 넘긴 근거 `{번호: 발행일}`(`available`)과 공시 기준일(`base_date`, 13F 분기 말)에 대조해 오류 문장을 돌려준다. 비면 통과. 검사: ① 1개 이상 골랐는가 ② 입력에 있던 번호인가(숫자가 아니면 없는 번호로 본다) ③ 같은 번호를 두 번 고르지 않았는가 ④ 발행일이 기준일 이전(같은 날 포함)인가. `where`("이유 1" 등)를 주면 문장 앞에 붙인다. DB를 읽지 않는다.
- **쓰는 곳**: C의 reasons.py `check_reasons` 안에 있던 날짜 검사를 이것으로 바꾼다(#85에서 B가 만들기로 함, 교체는 C 담당). 오류 문장을 `check_reasons`와 같은 말로 맞춰 두어 바꿔도 기존 테스트가 그대로 통과한다(`test_same_messages_as_reasons_check`가 확인).
- **주의할 점**: 기준일 당일 자료는 통과시킨다(reasons.py `load_evidence`가 `published_date <= base_date`로 고르는 것과 같음). ③ 중복 번호는 지금 reasons.py에는 없던 검사라 바꿔 끼우면 새로 걸릴 수 있다. 발행일·기준일이 `date`나 `YYYY-MM-DD`가 아니면 LLM이 고칠 수 없는 입력 데이터 문제라 오류 문장 대신 `ValueError`를 낸다. 근거 기간의 아래쪽(기준일 앞 92일)은 고를 때 정하는 것이라 여기서 보지 않는다. 카드 ③ 지금은의 "기준일 뒤 자료"는 반대 방향이라 이 함수의 대상이 아니다.
- **테스트**: `python -m pytest tests/test_evidence.py -q` (기준일 2026-09-30 손계산: 당일·이전 통과, 다음 날 실패, 빈 목록, 없는 번호, 문자열·True 번호, 중복, 여러 오류 순서와 `where`, date 객체 입력, 빈 입력, 잘못된 날짜 형식 5가지 ValueError, reasons.check_reasons와 같은 문장).
